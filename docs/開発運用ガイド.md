# 開発運用ガイド

このリポジトリを気持ちよく育てていくための、ゆるい運用ルールです。
（今回の整理で見つかった「つまずきポイント」への対策をまとめています）

## 1. フォルダを作りたいとき

Git は「空のフォルダ」を記録できません。GitHub の Web 画面でフォルダ名だけを
作ろうとすると、その名前のファイルが残ってしまいます（今回の残骸ファイルの原因）。

- 対策: フォルダには必ず中身を1つ入れる。まずは `README.md` を置くのがおすすめ。
- どうしても空にしたいときは、慣例として `.gitkeep` という空ファイルを置く。

## 2. コミットメッセージの型

一貫した型にすると、後から履歴を追いやすくなります。

```
<種別>: <何をしたか（日本語でOK）>

例）
feat: 診断結果にPDF出力ボタンを追加
fix: トップページのコピーを実態に合わせて修正
docs: READMEに構成ガイドを追記
chore: 不要ファイルを削除
```

- 1コミット＝1つの意味のまとまり。関連する変更はまとめてコミットする。
- 同じ内容のコミットを繰り返さない（今回 docs 作成コミットが重複していました）。

## 3. ブランチとプルリクエスト

- `main` は「いつでも公開できる状態」を保つ。
- 新しい変更は作業用ブランチを切ってから行い、プルリクエストでまとめて `main` に取り込む。
- `main` に push されると GitHub Pages へ自動デプロイされる点に注意。

## 4. AI（Claude Code）への頼み方のコツ

- ゴールと制約を先に伝える（例:「静的サイトとして GitHub Pages に出したい」）。
- 大きな作業は「まず設計 → 承認 → 実装」の順で分けると事故が減る。
- 「動くか検証して」と一言添えると、ビルド確認までやってもらいやすい。
